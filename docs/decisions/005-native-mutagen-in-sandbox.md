# 005: Native Mutagen/Synthesis API inside the sandbox

**Status:** accepted, September 2026. This supersedes the hand-written SDK and typed-edit protocol from design §5
and §6 and ADR 004's message set.

## Context

Scripts should have the full Synthesis/Mutagen API under the same names, so that a patch moves between SafePatch
and a native Synthesis patcher unchanged. Nobody should have to maintain a wrapper each time Mutagen changes.
A generated RPC proxy for every Mutagen interface was rejected. It would mean thousands of types, one round-trip
per property access, and a write-translation layer that still needs upkeep.

## Decision

**The script is a native patch function.** It is `public static void RunPatch(IPatcherState<ISkyrimMod, ISkyrimModGetter> state)`,
optionally `Task`-returning, in any public class. This is the same function a native patcher passes to
`SynthesisPipeline.Instance.AddPatch`.

**The worker runs the real Synthesis pipeline.** It calls
`SynthesisPipeline.Instance.AddPatch<ISkyrimMod, ISkyrimModGetter>(RunPatch).Run(args, fileSystem)` with the
exact arguments Synthesis passed to the host. State construction, load order, link cache, the seeded PatchMod
and output writing are therefore Synthesis's own code.

**Filesystem access goes through a read-only broker.** `fileSystem` is a `BrokeredFileSystem`, an in-memory
`MockFileSystem` from System.IO.Abstractions:

- Small inputs (the load-order file) are copied in as bytes.
- Plugins, BSAs and strings files are read-only handles. The host opens them, which works under MO2's VFS
  because the host is hooked. It then duplicates each handle into the worker with read access only.
- The host decides the file set from the parsed arguments. The worker never names a path for the host to open.
- Writes, including the output plugin, stay in memory. The worker returns the output plugin's bytes.

The OS sandbox is unchanged: the worker has no file, network, registry or process authority of its own.

**The host validates the output plugin generically, using Mutagen's generated code.**

- Each record that differs from the host's current `PatchMod` must be one of the following:
  - an override of a record visible to the host, where the changed fields are within the manifest's
    writable fields (for example `LeveledItem.Entries` or `LeveledItem.*`), or
  - a new record of a creatable type.
- Changed fields are found with the record's generated equals mask. Links are checked with the generated
  `EnumerateFormLinks`.
- Removing a record that the patch already contained is rejected.
- Accepted records are copied into the real `PatchMod` only after every record has passed.

## Consequences

- Agent code now holds real Mutagen objects, but only sandbox-local ones with no authority outside the worker.
  The OS sandbox and the host's output validation remain the boundary.
- The compiler allow-list now admits the Mutagen, Noggog and Loqui namespaces. It still denies System.IO,
  reflection and threads, and file paths are unreachable at runtime anyway. Of System.Drawing it admits
  `Color` and `KnownColor` only (System.Drawing.Primitives): Mutagen's records hold colours (an NPC's
  `TextureLighting`, a light's `Color`) as these values. `SystemColors`, which reads the OS's theme, and
  System.Drawing.Common's images stay denied.
- ADR 006 added nested records, autogenerated settings, loose assets through `state.AssetProvider` and
  FormKey persistence. The remaining limitation is that archives listed only in the game INI are not visible
  inside the sandbox (see ADR 006, "Findings").
